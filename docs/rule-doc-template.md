# 规则说明书编写模板（为检索而写，不是为人而写）

> 用法：复制本文件，改名为 `<游戏拼音>.md`，按注释填写后到管理端「规则文档」页上传。
> 上传后系统会**按 `##`/`###` 标题做语义分块**，每个章节成为一个完整检索单元，
> 并自动带上「《游戏名》/ 章节路径」上下文头参与向量化。
>
> ⚠️ **零虚构红线**：所有规则内容必须抄自真实规则书（官方 PDF / 说明书 / 授权中文版）。
> 不允许凭记忆或推测填写任何数值、流程、例外。查不到就留空并注明，
> 让 AI 如实回答「本站暂无该信息」，也不要编。

---

## 具体行动与费用
（填写：每种建造、交易操作的成本，精确到资源数量）

## YAML 前置元数据字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | 是 | 中文名，会写进每个切片的上下文头，直接影响检索归属 |
| `name_en` | 否 | 英文名，便于「Catan」这类英文提问命中 |
| `player_count` | 否 | 如 `3-4` |
| `play_time` | 否 | 如 `60-120 min` |
| `bgg_id` | 否 | BGG 条目 ID，便于溯源 |
| `language` | 否 | `zh` / `en` 等 |
| `source` | 建议 | 规则来源（哪本规则书、版本），便于日后核对真实性 |

---

## 正文四节的填写要求

### 1. 目标与胜利条件
- 精确到**数字**：获胜需要多少分、分数由哪些来源构成、各自值多少。
- 写清「同时达成」如何判定（平局/回合玩家优先/其他）——这是最常被问且最容易答错的。

### 2. 回合流程
- 按**发生顺序**写，用「1. 2. 3.」或分段，不要写成一段散文。
- 每个阶段写明「谁可以做、做什么、何时结束」。

### 3. 具体行动与费用
- 每种操作一行，成本**精确到资源数量**（例：道路 = 1 木材 + 1 砖块）。
- 保留所有前置条件（例：必须已有相邻聚落才能修路）。

### 4. 边界情况与例外（**最重要，最容易漏**）
- 争议点、罕见情况、规则书里的「注意」「例外」提示，全部保留。
- 原则：**不做简洁化处理**。AI 可以自己把细节总结成简短回答，
  但原文里没写的边界情况，RAG 永远答不出来。

---

## 分块行为说明（由 `backend/app/agent/rulebook.py` 执行）

1. **按标题切**：`##`/`###` 即语义边界，绝不把一条规则从中间截断。
2. **超长章节**：单节超过约 512 tokens 时，才退化为按段落/句子切，并保留约 12% 重叠。
3. **上下文头**：每片自动加 `【《游戏名》 / 章节路径】`，让 embedding 感知语义归属。
4. **自动清洗**：上传时先去除页眉页脚、页码（含 `第 N 页`/`Page N of M`）、PDF 乱码字符，
   以及重复 3 次以上的样板行——这些噪声会显著拉低检索质量。
5. **短章节不合并**：即使某节只有一句话，也独立成片，不并入相邻章节（避免语义混淆）。

## PDF 转写注意事项

- 扫描版图片 PDF 自动提取会**返回空**，需先 OCR 或换一个文字版 PDF。
- 提取后必须先做一轮清理（页眉页脚/页码/乱码），再转写成上面的 Markdown 结构。
- 术语优先采用**官方中文版**（如米宝海豚等国内代理发布的中文规则 PDF），
  避免机翻导致的术语不一致。
